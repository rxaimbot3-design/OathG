# Plan: Roadmap to 9.0+ Rating

## Current State: 7.5/10
Bugs fixed, tests pass, error handling improved. Remaining issues are **structural/architectural**, not bugs.

## Honest Gap Analysis: What 9.0+ Requires

### Blockers (Must Fix)
1. **Monolithic god files** — `discord-bot.ts` (5,392 lines), `server.ts` (3,272 lines), `SecurityFeatures.ts` (2,624 lines). Zero separation of concerns. Effectively unmaintainable.
2. **Global mutable static state** — 30+ static classes with internal Maps. Hidden coupling, race-condition risks, impossible to test in isolation.
3. **No process isolation** — Bot, web dashboard, C++ engine, Redis cache all run in one Node.js process. One crash = total outage.

### High Priority (Should Fix)
4. **Outdated dependencies** — `discord.js@14.27.0` (v15 available), `play-dl@1.9.7` (unmaintained, YouTube playback breaks), `prism-media` stale.
5. **Bot permission over-scope** — Requires `Administrator` to implement self-healing. If bot is compromised, attacker has full server control. Zero-trust premise broken.
6. **AI silent degradation** — On Gemini quota exhaustion, AI features silently return heuristic fallbacks without notifying operators or reducing load.

### Medium Priority (Nice to Have)
7. **C++ engine is scalar-only** — `kSimdAvailable = false`, no SIMD intrinsics despite advertising SSE/AVX2.
8. **No graceful degradation for Redis** — If Redis is down, some features silently fall back to in-memory, but operators aren't alerted.
9. **No rate limiting per-endpoint** — Global rate limiter exists, but heavy endpoints (backup, restore, bulk-ban-revert) don't have individual budgets.

## Implementation Plan

### Phase 1: Modularization (Est. 3-4 days)
**Goal:** Split god files into maintainable modules.

- **discord-bot.ts → `bot/`**
  - `bot/index.ts` — entry point, client init, event registration
  - `bot/commands/` — one file per command group (moderation, tickets, economy, music)
  - `bot/security/` — nuke defense, anti-raid, audit log handlers
  - `bot/self-heal.ts` — rollback/restore logic
  - `bot/guild-state.ts` — per-guild state trackers (recentWhitelistedActions, etc.)
- **server.ts → `server/`**
  - `server/routes/` — one file per route group (auth, security, backup, bot-control)
  - `server/middleware/` — auth, rate-limit, ip-ban, audit-log
  - `server/session.ts` — session management (Redis + local)
  - `server/health.ts` — health checks
- **SecurityFeatures.ts → `security/`**
  - `security/token-vault.ts`, `security/nuke-defense.ts`, `security/ip-ban.ts`, etc.
  - Keep `security/index.ts` for re-exports to minimize import churn

### Phase 2: Dependency Injection (Est. 2-3 days)
**Goal:** Remove static global state.

- Create `BotContext` / `SecurityContext` interfaces
- Pass instances via constructors instead of `static class.method()`
- Replace `Map<string, ...>` globals with scoped stores (e.g., `GuildStateStore` per guild)
- Add `destroy()` lifecycle methods for cleanup

### Phase 3: Upgrade Dependencies (Est. 1-2 days)
**Goal:** Fix outdated deps.

- Upgrade `discord.js` v14 → v15 (breaking changes in voice, intents, permissions)
- Replace `play-dl` with `@distube/ytdl-core` or `play-dl` fork
- Replace `prism-media` with `@discordjs/opus` + `ffmpeg-static` direct usage
- Update `play-dl` Spotify support or drop it

### Phase 4: Process Isolation (Est. 1-2 days)
**Goal:** One crash shouldn't kill everything.

- Move C++ engine to child process or separate worker (already has worker fallback)
- Move Redis operations to dedicated worker
- Implement health-check-based restart for isolated processes
- Use `worker_threads` or `child_process.fork()`

### Phase 5: Permission Scope Reduction (Est. 1 day)
**Goal:** Bot shouldn't need Administrator.

- Use hierarchy-aware permission checks
- For channel restoration: require `ManageChannels` only, not Administrator
- For role restoration: require `ManageRoles` only
- For unban: require `BanMembers` only
- Log failures when permissions are insufficient instead of silently continuing

### Phase 6: AI Degradation Visibility (Est. 0.5 days)
**Goal:** Operators know when AI is degraded.

- Add `aiQuotaExhausted` flag to dashboard status
- Emit webhook/alert on first quota exhaustion
- Back off AI scanning frequency on quota errors instead of silently falling back every message

## Recommendation
Do **not** attempt all 6 phases in one session. Start with **Phase 1 (Modularization)** as it unlocks everything else. Each phase should be a separate PR with its own test run.
